Membership Wizard Questions Step Proposed Schema

Mapping selected custom forms and custom questions to a membership type

This document proposes a clean persistence model for the Questions step: one membership type can select many reusable custom forms, and can also define many ad-hoc custom questions that are stored as a stable snapshot for later rendering.

1. Design Goal

Keep reusable forms separate from membership-specific questions

Reusable custom forms remain a catalog owned by the organizer. Membership types only store references to selected forms plus their own custom question definitions and ordering metadata.

Reusable form catalog

Organizer-created custom forms and their fields stay reusable across multiple membership types.

Membership-selected forms

A junction collection stores which reusable forms were picked for one membership type, with display order.

Membership custom questions

Ad-hoc questions are persisted as snapshot rows so they do not change if the source catalog changes later.

2. Proposed Entity Model
Entity Purpose Key fields Relationship
MembershipType Root membership aggregate with shared audit/identity behavior. Id, UniqueId, CreatedAt, CreatedBy, ModifiedAt, ModifiedBy, Name, Charges, Tenure Parent
MembershipForm Selected reusable custom forms. Id, UniqueId, MembershipTypeId, CustomFormId, DisplayOrder, IsDeleted Many per membership type
MembershipQuestion Membership-specific custom question snapshot. Id, UniqueId, MembershipTypeId, ControlTypeId, ControlLabel, PlaceHolder, Tooltip, IsMandatory, MinLength, MaxLength, DefaultValue, DisplayOrder, IsDeleted Many per membership type
MembershipQuestionOption Options for select / radio style questions. Id, UniqueId, MembershipQuestionId, Value, DisplayText, IsDefault, DisplayOrder, IsDeleted Many per question
3. Relationship Summary

Selected custom forms

These should be stored as an ordered collection of references to organizer custom forms.

  • Many-to-one from membership type to selected custom form rows.
  • Each row stores the selected CustomFormId.
  • DisplayOrder preserves drag-and-drop order from the UI.
  • Forms remain reusable and are not duplicated.

Custom questions

These should be stored as membership-owned rows with their own option child rows.

  • Many-to-one from membership type to question rows.
  • Question rows are snapshot copies of the control definition.
  • Options are stored separately for radio/select style controls.
  • DisplayOrder preserves the order shown in the wizard.

5. Save Flow
1. Load

Fetch membership type plus any selected forms and custom questions.

2. Persist

Save membership-selected forms as ordered junction rows and custom questions as owned snapshot rows.

3. Render

Rehydrate in the wizard and member-facing preview using the stored order values.

6. Recommended Rule Set
  • Do not duplicate reusable custom forms inside membership records.
  • Store selected custom forms as a reference list with order only.
  • Store custom questions as membership-owned snapshots so edits do not break historical setup.
  • Keep question options in a child table to support select/radio controls cleanly.
  • Persist order in both selected forms and custom questions.
  • Keep controller and service logic thin; let the service own the save rules.
7. Index Recommendations

These indexes are aimed at the most common fetch paths: load membership setup by membership type, load selected forms and questions in order, and load runtime submissions with their child answers quickly.

MembershipType

  • Index on UniqueId for direct lookup.
  • Index on OrganizerId for organizer-scoped filtering.

MembershipForm

  • Composite index on MembershipTypeId, DisplayOrder.
  • Index on CustomFormId for reverse lookup.

MembershipQuestion

  • Composite index on MembershipTypeId, DisplayOrder.
  • Index on ControlTypeId only if control-driven filtering is needed.

MembershipQuestionOption

  • Composite index on MembershipQuestionId, DisplayOrder.

MembershipSubmission

  • Index on UniqueId.
  • Composite index on MembershipTypeId, SubmittedAt.
  • Index on OrganizerId if organizer-wide reporting is common.

Response tables

  • MembershipFormResponse: index on MembershipSubmissionId, DisplayOrder.
  • MembershipQuestionResponse: index on MembershipSubmissionId, DisplayOrder.
  • MembershipQuestionResponseOption: composite index on MembershipQuestionResponseId, DisplayOrder.
8. Runtime Submission Schema

The setup tables above should not store user-entered answers. For member submissions, use a separate runtime model so answers remain stable even if the source custom form or question definitions change later.

MembershipSubmission

Parent record for a submitted membership application or enrollment.

public class MembershipSubmission : BaseAuditEntity, IUniqueId, IOrganizerId { public int Id { get; set; } public Guid UniqueId { get; set; } public int OrganizerId { get; set; } public int MembershipTypeId { get; set; } public int? MemberId { get; set; } public DateTime SubmittedAt { get; set; } public ICollection FormResponses { get; set; } = new List<MembershipFormResponse>(); public ICollection QuestionResponses { get; set; } = new List<MembershipQuestionResponse>(); }

Runtime storage rules

  • Keep answer storage separate from setup storage.
  • Snapshot labels and control metadata at submission time.
  • Store one child row per selected option when the field type supports multiple choices.
  • Preserve display order so answers render in the same order the user saw them.
  • Keep organizer ownership only on the aggregate roots; derive ownership for child tables through the parent relationship.
